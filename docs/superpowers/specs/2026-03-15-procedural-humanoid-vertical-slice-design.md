# Procedural Humanoid Vertical Slice

## Goal

Research prototype: a single procedural stylized humanoid walking through the Wrela Prism redwood scene, rendered through the existing visibility buffer pipeline with Demon Slayer art direction. The purpose is to explore what's possible at the intersection of procedural body generation, physics-informed motion, and declarative animation — optimized for learning and iteration, not production robustness.

## Approach

CPU skinning into static upload (Approach B). Each frame, the CPU evaluates the walk pose, skins the rest-pose mesh, and re-uploads deformed vertices into the GPU vertex buffer. The visibility buffer pipeline sees a new static mesh every frame — no rendering path changes required. The humanoid participates in the full pipeline: meshlet LOD, shadow maps, SSAO, material resolve, art direction, bloom, tonemap.

## Architecture

Four layers, each a Rust module:

1. **Body generation** — procedural skeleton + mesh from parameters
2. **Animation runtime** — pose evaluation, walk controller, IK correction
3. **CPU skinning** — deform vertices, re-upload to GPU
4. **Scene integration** — wire into existing SourceScene → RuntimeScene → Renderer flow

## Section 1: Skeleton & Body Generation

### Skeleton

A `HumanoidSkeleton` with ~22 bones in a parent-child hierarchy:

```
pelvis
├── spine_lower → spine_upper → neck → head
├── clavicle_l → upper_arm_l → lower_arm_l → hand_l
├── clavicle_r → upper_arm_r → lower_arm_r → hand_r
├── upper_leg_l → lower_leg_l → foot_l → toe_l
└── upper_leg_r → lower_leg_r → foot_r → toe_r
```

Each bone stores:

- Rest pose transform (local-space position + rotation relative to parent)
- Joint type: ball (shoulder, hip) or hinge (elbow, knee, ankle)
- Rotation limits: min/max per axis
- Rest length

Stored as a flat `Vec<Bone>` with parent indices — same pattern as the existing `TreeSkeleton` but with joint constraints added.

### Body Parameters

```rust
struct HumanoidParams {
    height: f32,
    head_scale: f32,
    shoulder_width: f32,
    torso_length: f32,
    leg_length_ratio: f32,  // relative to height
    arm_length_ratio: f32,
    muscle_bulk: f32,       // 0.0 lean → 1.0 heavy
    stylization: f32,       // 0.0 proportional → 1.0 exaggerated
    seed: u64,
}
```

### Mesh Generation

Body mesh generated by extruding cross-sections along each bone chain — reusing the approach from `tube_mesh.rs`. Each limb segment gets a radius profile (tapered cylinder/ellipsoid), and joints get blended overlap regions. Output is a `SourceTriangleMesh` with skinning weights baked alongside.

### Skinning Weights

Each vertex gets up to 4 bone influences (bone index + weight). These are stored CPU-side parallel to the vertex array — not uploaded to the GPU vertex buffer. Used only during the CPU skinning step.

### Material

A new `MATERIAL_SKIN` constant (ID 3). The material resolve shader gets a new branch for skin shading. Existing `semantic_channels` packed field encodes muscle definition, joint crease, surface curvature.

## Section 2: Animation Runtime

### Pose Representation

A `Pose` is a `Vec<BoneTransform>` parallel to the skeleton's bone array. Each `BoneTransform` is a local-space rotation (quaternion) + optional translation offset (for root bone world movement).

Evaluation: walk the hierarchy multiplying parent transforms — standard forward kinematics — producing `Vec<Mat4>` of world-space bone matrices.

### Walk Controller

```rust
struct WalkIntent {
    target: Vec3,
    speed: f32,
    style: WalkStyle,
}

struct WalkStyle {
    stride_length: f32,
    arm_swing: f32,       // 0.0 stiff → 1.0 relaxed
    spine_sway: f32,
    footfall_weight: f32, // 0.0 light → 1.0 heavy
    head_lead: f32,       // how much the head leads the body
}
```

The walk cycle is procedurally generated, not keyframed. The `WalkController` maintains a phase clock (0.0→1.0 per stride cycle) and computes bone rotations from sinusoidal basis functions modulated by style parameters. This is the core research question: how much of a believable walk can you get from parameterized functions vs. authored keyframes?

### Per-Frame Pipeline

1. `WalkController::update(dt, intent)` → `Pose` (bone local rotations)
2. `Pose::evaluate(skeleton)` → `Vec<Mat4>` (world-space bone matrices)
3. **IK correction** — two-bone IK on each leg to plant feet on terrain. Query ground height at each foot's projected position, adjust knee/ankle to match.
4. **Root motion** — pelvis translates forward along walk direction, with vertical bob derived from gait phase.

### No Physics in v1

The walk is kinematic with IK foot placement. Physics (balance, momentum, collision) is a later research question. IK correction provides physical plausibility without a full dynamics solver. The framing from the original conversation holds: the procedural cycle proposes, IK corrects.

## Section 3: CPU Skinning & Pipeline Integration

### Skinning

```rust
fn skin_mesh(
    rest_vertices: &[Vertex],
    weights: &[SkinWeights],  // parallel to vertices
    bone_matrices: &[Mat4],
) -> Vec<Vertex>
```

Each vertex's position and normal transformed by the weighted blend of its bone matrices (linear blend skinning). Output is a new `Vec<Vertex>` with identical topology — indices, meshlet structure, triangle count unchanged.

### Re-Upload

Deformed vertices replace the humanoid's region in the GPU vertex buffer each frame via `queue.write_buffer`. New method on `RuntimeSceneGpu`: `update_animated_vertices(prototype_id, &[Vertex])` that writes into the correct buffer offset.

Meshlet topology (index buffers, meshlet descriptors, group DAG) stays fixed. Only vertex positions and normals change.

### Bounding Sphere Staleness

Meshlet bounding spheres are computed from rest-pose vertices. A walking humanoid moves limbs ~0.5-1m from rest.

**v1 solution: conservative inflation.** Expand each meshlet's bounding sphere by a fixed skin radius at build time. The humanoid has maybe 8-15 meshlets — slight over-draw during culling is invisible.

### Shadow Pass

Shadow mesh also needs deformed vertices. Same skinning, same re-upload into shadow vertex buffer. One extra `write_buffer` call per frame.

## Section 4: Scene Integration

### Animation Directive (Proto-DSL)

```rust
struct AnimationDirective {
    actor: HumanoidParams,
    style: WalkStyle,
    action: Action,
}

enum Action {
    WalkTo { target: Vec3, speed: f32 },
    Idle,
}
```

Constructed in Rust code, passed to the runtime. The struct's shape is the proto-DSL — if the fields feel right after experimentation, parsing them from a file later is mechanical.

### New Files

| Location | Purpose |
|----------|---------|
| `src/subjects/humanoid.rs` | `HumanoidParams`, skeleton definition, body mesh generation |
| `src/subjects/humanoid_skin.rs` | `SkinWeights`, `skin_mesh()`, conservative bounding inflation |
| `src/animation/mod.rs` | `Pose`, `BoneTransform`, FK evaluation |
| `src/animation/walk.rs` | `WalkController`, `WalkIntent`, `WalkStyle`, procedural walk cycle |
| `src/animation/ik.rs` | Two-bone IK solver for foot placement |

## Out of Scope (v1)

- Facial animation, hands, fingers
- Physics simulation (gravity, momentum, collisions)
- Multiple characters
- Clothing, hair
- Blend shapes / morph targets
- Parsed DSL file format (the Rust struct is the interface)
- Terrain beyond the flat ground slab
- GPU skinning (CPU skinning is sufficient for one character)

## Future Research Questions

These are explicitly deferred — the vertical slice exists to inform which of these to pursue:

- How much of a believable walk can procedural sinusoidal functions achieve vs. authored keyframes?
- Where does CPU skinning + re-upload break down (character count, vertex count)?
- Can meshlet LOD meaningfully apply to animated meshes, or is it wasted?
- What does the walk controller's style parameter space actually look like — is it smooth and interpolatable?
- Does the Demon Slayer art direction style compose well with human figures, or does it need skin-specific tuning?
- What's the minimum viable physics layer (balance? momentum? contact forces?) that meaningfully improves the walk?
